0. КАК ПОЛЬЗОВАТЬСЯ ЭТИМ ФАЙЛОМ
--------------------------------------------------------------------------------

Задача агента-промптёра: превратить пожелание пользователя («в custom для LS1D
срезов не подтягиваются NT и eps») в промт, который сразу называет файл и
функцию. Исполнитель тогда идёт по адресу, а не тратит десяток поисков на
разведку.

Правило номер один: НАЗЫВАЙ ФАЙЛ И ФУНКЦИЮ. Разница на реальном примере —
8 поисковых вызовов против одного чтения файла.

Номера строк в этом документе — срез на дату выше и со временем разъезжаются.
В промте указывай ИМЯ функции/структуры, номер строки — только как подсказку
(«примерно gui.cpp:6445, проверь grep'ом по имени»).

--------------------------------------------------------------------------------
1. ЧТО ЭТО ЗА ПРИЛОЖЕНИЕ
--------------------------------------------------------------------------------

Десктопное GPU-приложение для анализа нелинейных динамических систем.

Сценарий: пользователь вводит систему ОДУ (LaTeX / обычный текст / фото через
OCR) → приложение генерирует исходник CUDA-ядра в рантайме → компилирует его
через NVRTC под текущую видеокарту → считает на GPU → рисует результат в
ImGui/ImPlot.

Что умеет считать:
  - фазовые портреты (2D/3D) и временные ряды;
  - бифуркационные диаграммы 1D и 2D;
  - старший показатель Ляпунова (LLE) 1D и 2D;
  - полный спектр Ляпунова (LS) 1D и 2D;
  - бассейны притяжения (basins of attraction);
  - 1D-ДПФ по параметру (DFT1D);
  - быструю синхронизацию (FastSync) по аттрактору и по сетке НУ.

Ключевая архитектурная особенность: данные остаются в памяти GPU, OpenGL
берёт их через interop без копирования на хост.

Платформа: только Windows 10/11 x64. Ни Linux, ни macOS не поддерживаются и
не планируются в коде.

2. СБОРКА И ДВЕ ТОЧКИ ВХОДА
--------------------------------------------------------------------------------

Сборка: MSBuild по .vcxproj. CMake НЕ используется, CMakeLists.txt в проекте
НЕТ (частая ложная догадка — не предлагай cmake).

  Решение:  D:\U-CUDA\U-CUDA.sln
  Проект:   D:\U-CUDA\U-CUDA\U-CUDA.vcxproj
  Тулчейн:  Visual Studio 2022, toolset v143, C++17 (stdcpp17), x64
  CUDA:     12.x / 13.x (в проекте прописан toolset "CUDA 13.0")
  Пакеты:   vcpkg manifest mode (vcpkg.json): glfw3, imgui (docking-experimental
            + glfw + opengl3), implot, implot3d
  Линкуется: cudart_static.lib, nvrtc.lib, cuda.lib, opengl32.lib

Команды сборки (собирать ИМЕННО решение):

  MSBuild U-CUDA.sln /p:Configuration=Release /p:Platform=x64
  MSBuild U-CUDA.sln /p:Configuration=Debug   /p:Platform=x64

  ВАЖНО: сборка напрямую по U-CUDA\U-CUDA.vcxproj кладёт .obj в другой,
  вложенный IntDir (U-CUDA\U-CUDA\x64\<Cfg>\) и в другой OutDir. Выглядит так,
  будто ничего не пересобралось. Всегда собирай .sln.

  Ещё: если приложение запущено, линковка Release падает с LNK1104 (exe занят).
  Закрыть приложение перед сборкой.

Выход:
  D:\U-CUDA\x64\Release\U-CUDA.exe
  D:\U-CUDA\x64\Debug\U-CUDA.exe

ДВЕ ТОЧКИ ВХОДА — ОДИН .EXE, РАЗНЫЙ main() (это задано ExcludedFromBuild
в .vcxproj):

  Release|x64: включён app_main.cpp, ИСКЛЮЧЁН main_NonLinAnal.cu
               → современный UI (ImGui/ImPlot, OCR, редактор ОДУ, NVRTC).
               Основной путь для пользователя.

  Debug|x64:   включён main_NonLinAnal.cu, ИСКЛЮЧЁН app_main.cpp
               → легаси-скриптовая точка входа (~4000 строк) с
               закомментированными шаблонами вызовов функций hostLibrary.cu.
               Обычно раскомментирован один вызов: посчитать, сохранить CSV.
               Используется для офлайн-исследований и пакетных прогонов.

Следствие для промтов: ЛЮБОЕ изменение сигнатур в hostLibrary.cu/.cuh надо
проверять сборкой ОБЕИХ конфигураций. Изменения только в UI-слое (gui.cpp,
app_model, *_session, plot_*) на Debug не влияют, но Debug всё равно должен
собираться.

Post-Build Event (одинаков в обеих конфигурациях) копирует в $(OutDir):
  ocr_server.py
  kernels\        (вся папка)
  cudaLibrary.cu, cudaLibrary.cuh, cudaMacros.cuh, configCUDA.h → в kernels\
NVRTC подхватывает эти заголовки в рантайме. Если после правки заголовка
рантайм-компиляция ядра ругается на пропавший символ — проверь, что файл
скопировался в OutDir\kernels\.
Внимание: library\ НЕ копируется — она резолвится от исходников в рантайме.

КОДИРОВКА (жёсткое правило, задано .editorconfig):
  *.c/*.cpp/*.h/*.cuh/*.cu и вообще всё, кроме списка ниже → UTF-8 С BOM
  *.json, *.md, *.yml, *.yaml, *.py, *.txt                → UTF-8 БЕЗ BOM
  ClCompile в обеих конфигурациях передаёт /utf-8.
Нужны обе половины. Без BOM Visual Studio угадывает CP1251 и портит русские
комментарии при сохранении; без /utf-8 MSVC перекодирует русские строковые
литералы в CP1251, и ImGui (он рисует UTF-8) показывает квадраты. Сборка при
этом успешна — поломка молчаливая.

4. СЛОИ И ПОТОК ДАННЫХ
--------------------------------------------------------------------------------

  [UI: gui.cpp]  — рисует кадр, читает/пишет состояние, кладёт задачи в очередь
        │
        v
  [Состояние: AppModel + *AnalysisSession + CustomSession]
        │  (сессия = «песочница» с копией системы, списком конфигов и результатов)
        v
  [Очередь: AppModel::*_queue + start_next_in_*_queue()]
        │  движок один, поэтому задачи драйнятся строго по одной
        v
  [Сессия: run_async(engine, idx) → std::future, poll() каждый кадр]
        │
        v
  [Кодоген: sysparse (парсинг ОДУ) → codegen (тело КРС на C/CUDA)]
        │
        v
  [Шаблон: kernels\<задача>.template.cu, в него подставляется тело КРС]
        │
        v
  [NVRTC: parametric_engine (все параметрические задачи) /
          nvrtc_engine + phase_portrait_nvrtc (фазовые портреты)]
        │  компиляция кэшируется по (тело КРС, размерность)
        v
  [Расчёт на GPU: ядра из шаблона + cudaLibrary.cu (интеграторы, DBSCAN, редукции)]
        │
        v
  [Result-структуры (*1DResult / *2DResult) → обратно в конфиг сессии]
        │
        v
  [Рендер: plot_renderer / plot_view_2d / plot_view_3d / heatmap_view,
           GPU-резидентные буферы через gpu_line_series*]

Отдельная ветка — легаси: main_NonLinAnal.cu вызывает hostLibrary.cu напрямую,
минуя UI, очереди, NVRTC-кодоген (там ядра компилируются обычным nvcc на этапе
сборки).

Вопрос «где хранится X» решается по этой лестнице:

  Глобальная настройка приложения (тема, шрифт, colormap по умолчанию,
      точность тиков, FMA)                    → AppModel + app_config
  Описание системы (уравнения, алфавит, схемы, НУ/параметры по умолчанию)
                                              → SystemRecord + library\*\system.json
  Что и как считать в конкретной вкладке      → соответствующий *Config
                                                 внутри *AnalysisSession
  Список конфигов, асинхронный запуск, результаты
                                              → *AnalysisSession
  Общая шапка пайплайна Custom                → CustomTabSharedConfig
  Раскладка окон, вкладки рабочего пространства
                                              → CustomWorkspace / imgui.ini
  Рабочее состояние между запусками приложения → sessions\_last*.json

ImGui — immediate mode: НИКАКОЕ состояние UI не должно жить в локальных
переменных между кадрами. Только AppModel / сессии / конфиги. Это правило
надо повторять в промтах, где добавляется новый виджет.

7. ЖИЗНЕННЫЙ ЦИКЛ ОДНОГО РАСЧЁТА
--------------------------------------------------------------------------------

 1. Пользователь жмёт Run в панели вкладки (draw_*_controls в gui.cpp).
 2. В очередь AppModel::*_queue кладётся элемент (индекс конфига или Kind).
 3. draw_gui каждый кадр зовёт start_next_in_*_queue(); если движок свободен —
    снимается один элемент.
 4. Для Custom: перед запуском вызывается apply_shared_to_*(shared, ..., слот)
    и pin_fixed_* — только здесь общая шапка попадает в слот подсессии.
 5. session.run_async(engine, idx) — собирает Request из строковых полей
    конфига (parse_d/parse_i), запускает std::async.
 6. ParametricEngine::run_*: берёт шаблон из kernels\, подставляет тело КРС от
    codegen (или сырое тело custom-схемы), компилирует NVRTC (или берёт из
    PTX-кэша), запускает ядро, собирает Result.
 7. session.poll() в кадре забирает future, кладёт результат в конфиг,
    выставляет last_run_ok / data_generation / fit_request.
 8. Рендер видит новый data_generation, перестраивает VBO и рисует; fit_request
    вызывает автомасштаб один раз.
 9. Custom дополнительно: commit_pending_signatures() продвигает pending →
    committed, чтобы следующий Run пропустил неизменившиеся уровни.

9. СЛОВАРЬ ПРОЕКТА
--------------------------------------------------------------------------------

КРС            — тело шага конечно-разностной схемы (то, что выдаёт кодоген и
                 что подставляется в шаблон ядра). В коде — krs_body, krs_code.
custom KRS     — пользовательская схема: сырой C/CUDA-текст вместо кодогена
                 (CustomScheme). Считается на GPU и на CPU (krs_cpu.cpp).
numb           — typedef в configCUDA.h, сейчас double. В CUDA-коде писать
                 ТОЛЬКО numb, не double/float.
AMOUNTOFX      — размерность фазового пространства (по умолчанию 3),
                 переопределяется #define перед include configCUDA.h.
a[0]           — коэффициент схемы (симметрия s у метода CD), НЕ параметр системы.
                 Параметры — a[1..M].
свип (sweep)   — прогон по диапазону: параметра, начального условия или шага h.
срез (slice)   — 1D-разрез 2D-карты вдоль одной оси при фиксированной второй.
                 В Custom: X-срез свипует X и пинит Y в fix_y, Y-срез наоборот.
слот [0]/[1]/[2] — фиксированная раскладка конфигов в подсессиях Custom:
                 2D / 1D-X / 1D-Y.
уровень (level) — этаж пайплайна Custom: L2D, L1D, L3.
сигнатура уровня — строка из всех входов уровня; равные сигнатуры = данные
                 совпадут, Run пропустит пересчёт.
continuation   — режим, где каждая точка свипа стартует с состояния предыдущей
                 (у LLE/LS переносится ещё и вектор возмущения). Только CPU.
NT / eps       — параметры LLE/LS: время между ренормировками и величина
                 возмущения.
writable_var   — переменная, по которой строится бифуркационная диаграмма;
                 -1 = комбинация x[0] + pi*x[1] + e*x[2].
pre_scaller    — прореживание (децимация) записи точек.
transient      — время, отбрасываемое перед сбором данных.
peak / interPeak — значения пиков и межпиковые интервалы; на БД можно рисовать
                 и то, и другое из ОДНОГО прогона.
DBSCAN         — кластеризация на GPU: определение периода в 2D-БД и разделение
                 аттракторов в бассейнах. Настройка — eps_dbscan.
mode_2d        — флаг в конфиге: считать карту (2D) вместо кривой (1D).
data_generation — счётчик версии результата; рендер по нему понимает, что пора
                 перестроить буферы.
fit_request    — одноразовый запрос автомасштаба после нового расчёта.

  9. ImGui immediate mode: состояние UI — только в AppModel/сессиях.
 10. Разделять логику UI и логику расчёта.
 11. LS требует numb = double: во float сжимающие показатели вырождаются в -inf.

Практические подсказки исполнителю (снижают расход и число ошибок):

    сигнатура уровня, вторая конфигурация);
  - чем проверять результат (какую конфигурацию собрать; что посмотреть в UI);
  - при работе с NVRTC — напоминание проверить копирование заголовков в
    OutDir\kernels\.

Шаблон:
    [Вкладка/режим] + [что не так или что добавить] +
    [файл: функция — точка входа] +
    [смежные места: ...] +
    [проверка: собрать Release/Debug, посмотреть ...]

Отдельно про формулировку задачи: если нужен только диагноз без правок —
сказать это прямо («только проверь, ничего не меняй»). Иначе исполнитель
по умолчанию доводит до рабочей сборки.

--------------------------------------------------------------------------------
12. ЧЕГО В ПРОЕКТЕ НЕТ (частые ложные допущения)
--------------------------------------------------------------------------------

  - Нет CMake. Нет CMakeLists.txt.
  - Нет автотестов, нет CI-конфигурации в репозитории.
  - Нет поддержки Linux/macOS: Win32-зависимости (ocr_client_win, диалоги
    файлов), MSVC-специфика, сборка только под VS2022.
  - Нет пакетного менеджера Python внутри C++-сборки: OCR-сервер запускается
    отдельно (requirements.txt, setup.ps1).
  - CLAUDE.md в корне местами устарел относительно кода: там не упомянуты
    режимы Dft1D и Custom, файлы custom_session.*, krs_cpu.*, digit_input.*,
    num_parse.h, grid_snap.h, а список шаблонов ядер неполный (нет dft1d_*,
    *_cont). Команда сборки там указана по .vcxproj — см. §2, почему лучше .sln.
    При расхождении верить исходникам, а не CLAUDE.md.
  - library\ не копируется post-build: она читается от исходников в рантайме.
